TRACE OF THE CURRENT IMPLEMENTATION

lib/model.js:490-499:
An unchanged individual save builds its normal where filter (including custom
conditions/version handling), applies read concern, then findOne()s with an _id
projection. A missing result becomes matchedCount=0.

lib/model.js:508-551:
The acknowledged save path checks affected counts and dispatches
DocumentNotFoundError through save error hooks. Versioned update failures can
instead produce VersionError; the scalar unchanged reproduction does not use that path.

lib/model.js:3682-3689 and 3992-4054:
bulkSave runs all pre-save hooks before building the batch. The builder validates
documents, emits inserts/updates, and filters out null operations for unchanged
documents. Classification therefore occurs after pre-save hooks/timestamps.
There is no existence read for the omitted inputs.

lib/model.js:3507-3514:
An empty operation list returns a synthetic BulkWriteResult without contacting MongoDB.

lib/model.js:3691-3703:
Non-MongoBulkWriteError failures propagate immediately. With no driver error,
matchedCount+insertedCount below the GENERATED operation count throws
MongooseBulkSaveIncompleteError. Unchanged inputs are absent from that comparison.
This error is an aggregate result check AFTER submitted writes, not rollback or
a server-side ordered stopping condition. Its existing document-count metadata
also uses the entire document array, so reusing it is a public-contract decision.

lib/model.js:3706-3727:
For per-operation driver errors, ordered batches map the first failing operation
back to its original input index and only handle preceding documents as successful.
Unordered batches exclude individually failed inputs and handle the rest, then
rethrow the bulk write error. If no error exists, all input documents go through
successful-write cleanup and post-save hooks, even skipped/missing unchanged inputs.

Ordered means stop at a server WRITE ERROR. A successful update matching zero
records is not itself a driver write error, and an omitted unchanged document
cannot produce one. Pre-save hooks have already run for all inputs in either mode.

READ / ROUND-TRIP COST AND UNRESOLVED DECISIONS

Measured commands AFTER collection initialization and data setup, restricted to
the operation being observed (monitorCommands=true):
- One unchanged save: 1 find.
- Unchanged-only bulkSave: 0 commands, whether the record exists or is absent.
- [update A, missing unchanged C, update D]: 1 update command carrying 2 operations,
  for default/true/false.
- Alternating mixed input [update A, insert B, C, update D, insert E]:
  default/ordered: 4 commands (update, insert, update, insert), each with 1 operation.
  unordered: 2 commands (one insert with 2 operations, one update with 2).
  Thus one bulkSave API call is not always one wire round trip.
- A separate experimental projected find over three unchanged IDs, one absent:
  1 find command; 2 IDs returned. This probe does not modify bulkSave.

A batched existence check adds one logical read (at least one find command for
the small cases measured), even when the current batch performs no database I/O.
Larger reads may need getMore commands. No timing benchmark or atomicity improvement
is claimed. Records can change between the check and writes.

The issue's proposed ordered behavior would require writing only the prefix
before the first missing input, then rejecting; simply preflighting and rejecting
everything would also skip valid prefix writes. Checking only after the entire
bulkWrite would allow later writes to persist. That choice is unresolved.
Unordered error aggregation and precedence with existing driver/incomplete-save
errors are also unresolved. The extra-read decision remains unresolved.
